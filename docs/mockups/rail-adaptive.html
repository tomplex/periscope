Adaptive rail + workspaces

The summary is always visible

Every pane keeps its narrator line — that's the whole point. A compact row is stripe + name + key metric (ctx%, PR#) plus the always-on summary line. Expansion does not reveal the summary; it adds metadata — model badge + the PR / Linear / git / time footer.

A pane lifts into a full B card only when selected or needs-input. So 29 panes stay scannable (~40px two-line rows), the focused/blocking one gets the full chip footer, and you never lose what a pane is doing. State rides the left stripe at both sizes.

Workspaces

A workspace (▧) is a named, top-level group interleaved among repos. Tabs are tagged into it (drag, or /api/workspaces/tag) — so it pulls panes from across repos/worktrees into one effort.

Here attribute-config gathers the FDY-2637 work that physically lives in three different fdy worktrees. Each card keeps a faint ⎇ origin-worktree tag so you don't lose where it actually is. An empty workspace shows a dashed drop target.

Two illustrative states

Your live rail had no needs-input pane, so I flipped config-migration-skill to needs-input and expanded ci-python-rewrite (done) to show both auto-expand triggers. Everything else is your real data.

Open question

Should working panes (actively burning tokens) also auto-expand, or only selected + needs-input? Auto-expanding working would surface live progress but re-inflates the rail when you've got many going at once.
